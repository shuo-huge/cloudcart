# CloudCart Architecture

## 1. Runtime topology

One store = one Worker + one D1 database + one R2 bucket + one static-asset bundle.

```
Browser ──► Cloudflare edge
             ├─ Workers Static Assets  /static/*, /admin/static/*
             └─ Worker (Hono)          /, /api/*, /admin, /admin/*, /media/*, /webhooks/*
                 ├─ D1  (SQLite)       products, orders, pages, settings, sessions…
                 └─ R2                  product images and uploaded media
```

- Static assets are served by the edge before the Worker executes when a file matches.
  `/api/*`, `/webhooks/*`, `/media/*`, `/sitemap.xml`, `/robots.txt` and `/setup` are configured
  with `run_worker_first`.
- The admin SPA shell is at `dist/admin/index.html`; its JS/CSS are served from
  `/static/admin-ui/assets/*` (Workers Static Assets). Deep links under `/admin/*` are handled by the
  Worker, which returns the shell.
- Public storefront pages are rendered **server-side** as HTML strings, so product names,
  descriptions and schema.org data are crawlable without JavaScript.

## 2. Monorepo packages

| Package | Responsibility |
|---|---|
| `apps/worker` | HTTP surface (Hono), SSR wiring, auth middleware, webhooks, static/media serving |
| `apps/admin` | Preact SPA: all admin screens and the visual page editor |
| `apps/storefront` | Small client bundle: server-cart interactions, newsletter forms |
| `packages/core` | Business rules: auth, products, categories, media, coupons, shipping, cart, orders, payment events, pages, themes, SEO, storefront data assembly |
| `packages/database` | D1 prepared-statement wrapper, row types, resource guard |
| `packages/security` | PBKDF2, HMAC sessions, AES-GCM/HKDF secret encryption, HTML sanitiser, security headers |
| `packages/shared` | Money (integer minor units), slugs, ids, countries, shared types, escaping |
| `packages/plugin-sdk` | Plugin and payment interfaces |
| `packages/theme-sdk` | Theme interface, HTML helpers, `createTheme` kit |
| `plugins/*` | Build-time bundled plugins (manual, Stripe, PayPal) |
| `themes/*` | Eight bundled themes |

Core depends on `@cloudcart/plugin-sdk`'s **interfaces**, never on Stripe, PayPal or a concrete theme.
The Worker composes concrete plugins/themes at its edge (`plugin-registry.ts`, `theme-registry.ts`).

## 3. Request flow

### Storefront page
1. Route handler builds a `Storefront` service with the active theme, store settings and cart count.
2. Data is loaded through paginated, indexed D1 queries (count + page in one `db.batch`).
3. The theme returns body HTML using the same data model for all eight themes.
4. `renderDocument` wraps it with SEO metadata, JSON-LD, token CSS, theme CSS and the hashed JS/CSS
   asset paths generated by `scripts/generate-assets.mjs`.

### Cart
- The cart lives in D1. A random 32-byte token in an HttpOnly cookie maps to `carts.token` (stored
  as a SHA-256 hash). Browser storage is never trusted for prices.
- `loadCart` joins products/variants/images in one query and recomputes prices, availability,
  coupon discount and shipping estimate.
- Cart pages are rendered server-side from the cookie, so quantity/removal work without a
  client-side cart model.

### Guest checkout (atomicity)
1. Re-load and validate the cart from D1 (active products, variant validity, stock, coupon rules,
   shipping rate for the destination).
2. Reserve the coupon usage with a conditional `UPDATE … WHERE used_count < max_uses`.
3. Reserve stock with conditional `UPDATE … WHERE stock >= quantity` per managed line. If any line
   fails, already-reserved stock is compensated and the order is refused.
4. Insert order, item snapshots, address snapshots, coupon redemption, inventory movements, customer
   aggregates, and delete the cart — in one atomic D1 batch. On batch failure, stock and coupon
   reservations are compensated.
5. Manual payment → `awaiting_manual_payment`. Online provider → `pending_payment` and a provider
   session is created; the customer is redirected to the provider.

### Payment events
```
Provider ──► /webhooks/{stripe|paypal}
             1. Verify signature (raw body for Stripe; PayPal verify API for PayPal)
             2. Build a PaymentEvent {eventId, amount, currency, order identifiers…}
             3. Resolve the internal order (metadata / provider order id → transaction)
             4. INSERT OR IGNORE payment_events (unique plugin+event id)
             5. Compare amount and currency with the order
             6. Atomically mark transaction succeeded + order paid
```
Duplicated deliveries return `result: "duplicate"` and change nothing. Amount/currency mismatches are
recorded and never mark an order paid. Cancelled/refunded orders stay closed.

PayPal’s return URL captures server-side, then feeds the **same** event pipeline with a capture event.

## 4. Order state machine

```
draft → pending_payment → paid → processing → shipped → completed
  │            │              └──────────────► cancelled / refunded / partially_refunded
  │            └────────────► awaiting_manual_payment → paid
  └────────────► cancelled
```

Transitions are enforced server-side (`canTransition`). An administrator cannot set `paid` for a
non-manual provider; that only happens through a verified payment event. Manual confirmation records
the admin id and timestamp in `payment_transactions` and the audit log. Fulfilment details
(`shipping_carrier`, `tracking_number`, `tracking_url`) are edited by the administrator and shown on
the customer’s order page.

## 5. Data model (D1)

Migrations: `migrations/0001_init.sql`, `0002_cart_fields.sql`.

Tables: `admins`, `admin_sessions`, `installation_state`, `store_settings`, `products`,
`product_variants`, `product_images`, `categories`, `product_categories`, `product_tags`,
`inventory_movements`, `customers`, `customer_addresses`, `carts`, `cart_items`, `orders`,
`order_items`, `order_addresses`, `payment_transactions`, `payment_events`, `shipping_zones`,
`shipping_rates`, `coupons`, `coupon_products`, `coupon_categories`, `coupon_redemptions`,
`plugins`, `plugin_settings`, `themes`, `theme_settings`, `pages`, `page_versions`, `media`,
`audit_logs`, `redirects`, `newsletter_subscribers`, `login_attempts`, `resource_usage`.

Conventions:
- Money is `INTEGER` minor units; currency is ISO-4217.
- Timestamps are ISO-8601 UTC text.
- List queries are paginated and use indexes on slug, status, dates, emails and foreign keys.
- Every dynamic value goes through D1 prepared statements; no SQL string concatenation of user input.
- `payment_events(plugin_id, event_id)` is unique; `coupon_redemptions(order_id)` is unique.

## 6. Pages and the editor

- `pages.draft_json` holds the editable JSON; `page_versions` holds immutable published snapshots;
  `pages.published_version` points at the live one.
- Drafts are private: the public storefront only reads the published version.
- Editor preview calls `POST /api/admin/pages/:slug/preview`, which validates the draft and renders
  it through the real active theme into an iframe `srcdoc`.
- Page JSON is validated server-side (section count, size, shape). Any `<script` is rejected.
- Section presentation settings (background, text colour, padding, alignment, max-width, font) are
  emitted as an inline `style` on a wrapper only after allow-list validation in `frameSection`.
- Custom HTML is sanitised with a strict allow-list sanitiser (no scripts, iframes, event handlers
  or `javascript:` URLs).

## 7. Caching and performance

- HTML is `private, no-store`/`must-revalidate` because the header contains the visitor’s cart count.
  Data-level caching is deliberately avoided until it can be invalidated correctly.
- Static JS/CSS use content hashes and immutable caching.
- Media from R2 is immutable with a one-year cache and `nosniff`/sandbox headers.
- Each request stays within the 50-subrequest budget: no per-item fetches, no external APIs on
  storefront reads, batch queries for counts + lists.

## 8. Resource limits

See `docs/FREE_TIER_BUDGET.md`. Design rules: paginate every list, prefer one `db.batch` over
multiple round-trips, avoid `SELECT *` for public lists, avoid large SSR frameworks, never convert
images to base64 in D1.
